@AGENTS.md

## Project context

Booking schedule app for a small nail (整甲) and eyelash (眼睫毛) studio. It is a rewrite of an existing **Google AppSheet** app whose data lives in a **Google Sheet**; the new Expo app must reuse that existing sheet data rather than migrate to a new database.

Two users, both writing to the same schedule:
- The owner's daughter arranges times with customers over WhatsApp, then records the booking in the app.
- The studio owner sometimes books customers herself.

Because the AppSheet app may stay in use during the transition, treat the Google Sheet as the single source of truth and don't change its column layout.

All UI copy is Traditional Chinese. Keep new strings in the same language and tone.

## Commands

The project uses **npm** (`package-lock.json`), so use `npx`, not `bunx`.

```bash
npm start                 # expo start on port 8080 (also: npm run ios / android / web)
npm run start:tunnel      # expo start behind a Cloudflare tunnel (ngrok --tunnel fails); needs cloudflared
npm run lint              # expo lint
npx tsc --noEmit          # typecheck
npm test                  # jest (jest-expo preset); npm test -- <path> for one file
```

Tests sit next to the code as `*.test.ts` (never under `src/app/`, where every file is a route) and cover pure logic only. Import `describe` / `it` / `expect` from `@jest/globals`: TypeScript 6 doesn't load `@types/*` globals by default. `src/test/` holds shared fixtures such as `makeAppointment`. Jest's `modulePaths` includes `node_modules/expo/node_modules` because `expo-modules-core`, which the preset loads, is installed only there.

## Architecture

Expo SDK 58, Expo Router with typed routes, and the `@/*` → `src/*` path alias. The UI mirrors the existing AppSheet app (`reference/timetable.png`). The root `Stack` holds the `(tabs)` group and the `add-appointment` modal, which accepts optional `date` / `customerName` params for prefilling, or an `id` param to edit that appointment. Tapping an appointment (timetable or list) opens the `appointment-details` modal (a folder with its own `Stack`, so on iOS its customer row pushes `appointment-details/customer`, the `customer-details` screen with a back button instead of ✕, inside the sheet; Android and web open the `customer-details` modal), which has 修改 (the detail modals have no WhatsApp button; WhatsApp lives on the list rows). On iOS, 修改 turns the same sheet into `AppointmentForm` (`src/components/swiftui/`, the form the `add-appointment` route also renders; its rules, validation and save live in `useAppointmentForm`, shared with the Android / web `add-appointment` screen, so pricing or duration changes go there once) with 刪除預約 at the end; on Android and web it replaces itself with `add-appointment` in edit mode, next to a 刪除 button. Both look the appointment up with `findCachedAppointment`, so it must already be loaded. Tabs, in the same order on every platform (iOS uses `(tabs)/_layout.ios.tsx`: `NativeTabs`, the native Liquid Glass tab bar, which draws no headers, so each iOS screen draws its own title, e.g. a SwiftUI `NavigationStack`; Android and web use the JS `Tabs` in `_layout.tsx`). There's no 預約 tab: new bookings start from the ＋ buttons on the list and timetable screens. The tab bar hides while scrolling down and comes back on scroll up: both layouts wrap their tabs in `TabBarVisibilityProvider` (`src/hooks/useTabBarVisibility.tsx`, which keeps `hidden` in its own context so toggling the bar doesn't re-render the screens), and each scrolling screen reports its offset with `useHideTabBarOnScroll` (spread `scrollHandlers` onto RN scroll views) or, in SwiftUI, with `...useHideTabBarOnScrollModifiers()` from `src/components/swiftui/hideTabBarOnScroll.ts`. Only offsets that change while the user drags or flings count, so layout shifts can't toggle the bar back. iOS hides the native bar via `NativeTabs hidden` and animates it however the system does (it can't be made to slide); keep the native bar there for its floating shape and touch effects. On Android and web, `SlidingTabBar` (`src/components/`) floats the stock `BottomTabBar` over the screens and slides it with a native-driver transform, so screens pad their scroll content by `useTabBarInset()` (0 on iOS), and `AddButton` slides with the bar.
- `stats` (統計, added after the AppSheet tabs): dashboard over the last 12 months, loaded with one open-ended `useAppointments({ from })` call. Calculations are in `src/utils/stats.ts` (特別事項 and rows without a customer are skipped), charts in `src/components/stats/` (plain Views, no chart library).
- `customers` (顧客資料): on iOS the list renders 50 rows more each time the end comes near, since @expo/ui `List` mounts every row. Tapping a customer opens the `customer-details` modal, which edits the name/phone in place or deletes the 顧客 row (found via `findCachedCustomer`), and shows their booking history (`useCustomerAppointments`, rendered by `CustomerHistory`). Its ＋ button opens the `add-customer` modal, prefilled from an unmatched search. On iOS, long-pressing a row opens a SwiftUI `ContextMenu` with 修改 (`customer-details` with `edit=1`, which opens in edit mode) and 刪除 (confirmed with a SwiftUI `Alert`, since an iOS 26 `ConfirmationDialog` opens as a popover that hides its cancel button).
- `appointments` (預約資料): upcoming list.
- `index` (時間表, home): Day/Week/Month calendar, built from `src/components/calendar/` (`MonthView`, and `TimeGrid` for Day and Week, with the block positions and overlap lanes in `layoutBlocks.ts`, and each booking drawn by `TimeGridBlock`; its iOS version is SwiftUI, where a long press opens a `ContextMenu` with 修改 (the `add-appointment` route in edit mode) and 刪除 (confirmed with a `ConfirmationDialog`)). Both re-render each minute (`useNow`), so today's marker and the now line stay current. Swiping pages to the next / previous month, week or day (helpers in `calendar/timetablePages.ts`): on iOS `TimetablePager` (`src/components/swiftui/`) puts the pages in a SwiftUI page-style `TabView`, so they slide under the finger as in iOS Calendar; it keeps a window of pages around the anchor and draws only the one on screen and its neighbours, from the cache (`useCachedAppointments`, which doesn't load) that the screen prefetches. Android and web use `useSwipePaging`, a `PanResponder` that only takes clearly horizontal drags, so scrolling and taps still work. Tapping the 時間表 tab while on it goes back to Month view (`useTabReselect`, which listens for `tabPress` while the screen is focused).

`useAppointments({ from, to })` (`src/hooks/`) loads a date range and reloads on focus. The timetable fetches the whole month grid at once, so switching views within a month doesn't call Apps Script again. Its cache and the customer list (`useCustomers`) are also saved on the device through `src/utils/persistentStorage.ts` (the appointments in the format in `src/utils/storedAppointments.ts`) (expo-sqlite's kv-store, read synchronously at startup; `localStorage` on web; the newest 24 ranges are kept, each booking saved once with ranges holding only ids, since they overlap), so screens open with the last data at once after a restart and Apps Script refreshes it in the background. Dev builds without the `ExpoSQLite` native module just skip saving. Bump the storage keys' version (`appointments-cache-v3`, `customers-cache-v2`) if the `Appointment` / `Customer` shape changes. Appointment saves and deletes don't wait for Apps Script (several seconds per write): the forms and details screens call `saveAppointment` / `removeAppointment` (`src/hooks/appointmentWrites.ts`), which change the cache at once (`setPendingAppointment`), close the screen, and send the write in the background, one at a time in order. The queue (`writeQueue.ts`) is an outbox saved on the device before the screen closes (each write as a kind and payload, registered with `defineWrite`), so writes a closed app left unsent are shown again and resent at the next launch (`useResumeWrites` in the root layout). Writes must therefore be safe to send twice: a new booking gets its real 22-char 預約ID in the app (`newAppointmentId`), which Apps Script uses and, on a repeat, answers with the row it already made. Edits or deletes of a booking still being created wait for its create. Every Apps Script call gives up after 60 s (`request` in `appointmentsApi.ts`), since Android's networking has no timeout and one stalled request would hold up every write behind it. Reloads re-apply writes still pending or finished since the reload started, so they can't undo them, and a failed write is undone in the cache and reported with `showAlert` (the only message a save shows). Hooks re-render when their own range's cache changes (`useSyncExternalStore`), or on any change while they're still showing a covering range. A range not loaded yet shows what a wider cached range holds for it while it loads, which is what makes the 補甲 / 補眼睫毛 price instant. Customer adds, edits and deletes work the same way through `saveCustomer` / `removeCustomer` (`src/hooks/customerWrites.ts`, in the same queue, `writeQueue.ts`): a new customer is keyed by name until its 顧客ID comes back, and a rename also renames their cached bookings (`renameCachedCustomer`), as the script does in the sheet. 新增顧客 then asks whether to book them straight away. Reloads that find nothing changed keep the same objects (`reuseUnchanged`), so screens don't re-render. Date helpers in `src/utils/dates.ts` work on `YYYY-MM-DD` strings, with weeks starting on Sunday.

On web, `Alert.alert` from react-native-web is a no-op. Use `showAlert` from `src/utils/alert.ts`, which falls back to `window.alert` / `window.confirm`.

**Data flow:** screens never touch data sources directly. They call `src/services/appointmentsApi.ts` (`listAppointments`, `createAppointment`, `updateAppointment`, `deleteAppointment`). That module talks to the Google Apps Script Web App in `apps-script/Code.gs`, using `EXPO_PUBLIC_APPS_SCRIPT_URL` and `EXPO_PUBLIC_APPS_SCRIPT_TOKEN` from `.env.local` (see `.env.example`). When the URL is empty, it falls back to `src/data/mockAppointments.ts`, and the mock writes don't persist.

**Apps Script** (`apps-script/`, deployed by hand. Setup steps are in `apps-script/README.md`):
- Every response is HTTP 200 with JSON `{ ok, ... }` or `{ ok: false, error }`. Actions are `listAppointments` (with `from`/`to` filters), `listCustomers`, `listCustomerAppointments` (by `id`/`name`, any date) and `ping` via GET, and `createAppointment`, `updateAppointment` (by 預約ID, writing only the known columns) `deleteAppointment` (removes the row), `createCustomer` (new 顧客ID shaped like the existing ones), `updateCustomer`, `deleteCustomer` and `registerPushToken` via POST; appointment writes also push the change to the other phones (see Notifications). Customers are keyed by 顧客ID, or by name when a row has none. Renaming a customer also renames the 預約資料 rows that store the old name; deleting one rewrites rows that store its 顧客ID to the name, so bookings stay readable.
- POST bodies are sent as `text/plain` so web builds skip the CORS preflight, which Apps Script can't handle.
- The script reads which spreadsheet to use from the `SPREADSHEET_ID` Script Property. During development that's a **copy** of the real data. Switching to the real sheet only changes this property, so never hard-code a spreadsheet ID.
- Columns are looked up by header name. Times are parsed from display strings, not raw values, because time-only cells come back as 1899 dates with odd Asia/Hong_Kong offsets. Dates are parsed from their `yyyy/M/d` display text too: one `Utilities.formatDate` call per row added about 5 s to every read, so keep per-row service calls out of loops. Whole-column scans (the date-range scan, finding a 預約ID) use `getValues`, not `getDisplayValues`, which is several times slower on ~4,000 rows; the range scan compares date cells as timestamps. Writes read only the 預約ID column and the last 200 rows (for the sheet's Duration / 顧客ID style), not the whole sheet.
- Writes happen under `LockService`, since both users may save at the same moment. Repeating a write is harmless, as the app may resend one (see the outbox above): `createAppointment` takes the app's `id` and returns the existing row if one has it (no push then), deleting a booking or customer that's gone succeeds, and `createCustomer` with a name and phone that already exist returns that customer. Typed text (names, 備注, View) goes through `plainText_`, which adds a hidden leading apostrophe to values starting with = + - @ so Sheets keeps them as text instead of a formula. Code changes have to be redeployed as a new version of the existing deployment, which keeps the `/exec` URL.

**Sheet ↔ type mapping** lives in `src/types/appointment.ts`, which documents the sheet tabs and their columns:
- `預約資料` (appointments): 預約ID, 活動, 備注, 顧客姓名, 日期, 時間, Duration, 手/腳, 收費, 狀態, End Time, View, 訂金, 複雜款, 拆甲, 延長, 訂金處理 (訂金處理 holds `保留` when the customer keeps a paid deposit for their next booking: `keepDeposit`. It's set by the 保留訂金 button in the appointment details (customer bookings with 訂金 paid, not No show; `KeepDepositButton`, a SwiftUI button and alert, on iOS, `askKeepDeposit` in `src/utils/appointmentActions.ts` elsewhere), which saves it with `saveKeepDeposit` and leaves 狀態 alone; once set, the button reads 取消保留訂金. The iOS Day / Week long-press menu (`TimeGridBlock.ios.tsx`) has the same item, saved without a confirm like No show. It's only a note, with no amounts; the forms don't send it, so edits leave it alone. The script writes it only when sent and, when turning it off, clears only a `保留`. The booking details and the form show 上次預約（date）保留了訂金 when the customer's previous booking (`previousKeptDeposit` in `src/utils/keptDeposit.ts`, skipping No show) kept it, and 顧客資料 lists the bookings marked 保留 under 保留訂金記錄. The sheet's 實收 column and `訂金紀錄` tab aren't used; View holds the customer's name on every booking, as AppSheet does; the script fills it unless sent, and 特別事項 sends 備注. Duration is the booking's full length including add-ons, and End Time = 時間 + Duration; older AppSheet rows that keep Duration at the service default (2:30:00 for every 整甲) are a deprecated flow, as is the 粉嫩術時間 column, which the app ignores; 訂金 (a "paid" flag) is used by every service but 特別事項 and starts on paid for new bookings, and the 整甲 add-ons by 整甲 and 整甲 + 眼睫毛: 複雜款 holds 不是複雜款 / 半個鐘 / 一個鐘 (`COMPLEX_DESIGN_OPTIONS`), and 拆甲 / 延長 (`NAIL_EXTRAS`) are TRUE / FALSE like 訂金 (`FLAG_COL` in `Code.gs`). All of these are written only when sent, and the script errors if one is sent but its column is missing). The top-ups' default 收費 depends on the customer's last full set before the booking date (`src/utils/topUpPrice.ts`, which the forms also show under 收費): 補眼睫毛 after 眼睫毛 is $0 within 5 days, $214 within 14 days, else $428; 補甲 after 整甲 is $0 within 5 days, else $30
- `顧客` (customers): 顧客ID, 顧客姓名, 電話, plus IG and 加入日期, which 顧客資料 shows (read-only) as an IG link button (on iOS `InstagramButton` in `src/components/swiftui/`, the white logo `assets/images/instagram.png` and @name on an accent glass button; `src/utils/instagram.ts` turns the cell's profile link or @name into a clean URL) and the join date. `createCustomer` fills 加入日期 with the day, as AppSheet does; edits leave both alone. The AppSheet-only columns (預約資料's 完成作品 photo paths, 顧客's Phote, Package, 使用次數) aren't read; creates leave them blank and edits don't touch them

Real-data conventions (from AppSheet): 狀態 is `預約` / `已完成` (blank for 特別事項), plus the app's `No show` (`NO_SHOW` in `src/types/appointment.ts`), set from a long-press menu on customer bookings (SwiftUI `ContextMenu` on the iOS timetable blocks and list rows, an alert on Android, none on web) next to 顧客資料, which opens `customer-details`; `saveAppointmentStatus` sends the row as it is with only 狀態 changed. No show bookings are faded in the timetable and left out of `isCustomerBooking` (stats, widget, notifications) and of the top-up price's last set. New 預約ID values are 22-char alphanumeric. The service list and each service's default Duration and 收費 live in `src/constants/services.ts`. `defaultDurationFor` / `defaultPriceFor` take the form's 手/腳 and add-ons: 整甲 is 2 h / $218 for 手, 1 h / $298 for 腳 and 3 h / $516 for 手 + 腳, 整甲 + 眼睫毛 is 整甲's time and 收費 for the same 手/腳 plus 眼睫毛's 2 h / $428 (4 h / $646 for 手), and 整甲 and 整甲 + 眼睫毛 add 30 min / $0 for 拆甲, 60 min / $100 for 延長, and 30 min / $60 or 60 min / $120 for 複雜款 半個鐘 / 一個鐘. 腳 bookings hide these add-ons and save them cleared. A new 整甲 or 整甲 + 眼睫毛 starts with 拆甲 on. The forms keep 收費 on this default (or the top-up price) until it's typed by hand; edits open with the sheet's 收費 and switch to these rules once the service, 手/腳, an add-on or (for top-ups) the customer or date changes. Duration always follows these rules, in edits too, so saving an older row rewrites its Duration and End Time to the full length. End Time = 時間 + Duration, or 時間 itself when there's no duration; 特別事項 is the exception, where the form asks for 完結時間 and Duration = End Time − 時間.

The `Appointment` type uses English field names. `phone` comes from a join with `顧客` by customer name, done either client-side or in Apps Script. Dates are `YYYY-MM-DD` and times are `HH:mm` (24h) strings. `groupAppointmentsByDate` depends on sorting these strings lexically, so keep that format when you parse the sheet's values.

**Home screen widget (iOS only):** `src/widgets/TodayWidget.tsx` (`expo-widgets`, configured in `app.json`, small and medium) shows today's booking count and the next booking. Its `'widget'` component runs in an isolated runtime, so it can't fetch or import anything; the app pushes data instead. `useUpcomingSync` (`src/hooks/`, called in the root layout) loads `{ from: today }` through the `useAppointments` cache (`loadAppointments`, the 預約資料 tab's range, so they share one call) and keeps the next two weeks, on launch, on returning to the foreground, after every write (`onAppointmentsChanged` in `appointmentsApi`) and on a change push, then hands them to `updateTodayWidget` (a no-op off iOS), where `buildTodayWidgetTimeline` turns them into timeline entries at each midnight and booking start, and to the local notifications. Needs a development build, not Expo Go; where the `ExpoWidgets` native module is missing (Expo Go, older builds), `updateTodayWidget` does nothing instead of crashing.

**Notifications (iOS and Android):** `src/notifications/`, with `expo-notifications`. Each phone schedules its own local notifications (`buildLocalNotifications` in `localNotifications.ts`): a reminder 1 hour before each customer booking and a 09:00 summary on days with bookings (特別事項 skipped, at most 60 at once because iOS keeps 64). `scheduleLocalNotifications` replaces them all on every sync. Booking changes reach the *other* phone by push: `useNotifications` (root layout) asks for permission, gets the Expo push token (needs `extra.eas.projectId`; skipped without it) and registers it with Apps Script (`registerPushToken`, kept in the `PUSH_TOKENS` script property, not the sheet), and booking writes send that token as `pushToken` so the script skips the sender. The script sends a visible message on the `changes` Android channel plus a silent `contentAvailable` one; `backgroundSync.ts` runs `syncUpcoming` for it, even with the app in the background. That task must be defined before the app loads, so the entry is `index.ts`, which imports it before `expo-router/entry`. Tapping a notification with `appointmentId` in its data opens `appointment-details` if that booking is cached. Where the native modules are missing (Expo Go, web, older builds) all of this does nothing. Setup (EAS project, APNs, FCM) is in `apps-script/README.md`.

**WhatsApp:** `src/utils/whatsapp.ts` opens `https://wa.me/<digits>` through `expo-linking`. Phones should be digits only with the country code (Hong Kong `852…`). `AppointmentCard` hides the WhatsApp button when there is no phone. WhatsApp buttons are icon-only with the WhatsApp logo (`assets/images/whatsapp.png`, white on transparent): `WhatsAppButton` in `src/components/swiftui/` on iOS (SwiftUI `Image` needs a local file, so it goes through `expo-asset`), `WhatsAppIcon` inside the green round `Pressable` elsewhere. Give them an `accessibilityLabel`, since there's no text. After a new booking for a customer with a phone (not 特別事項) is saved, the app asks whether to send a WhatsApp confirmation (`confirmationMessage`), with 稍後 / 發送確認訊息: `useAppointmentForm` calls `offerWhatsAppConfirmation`, which queues the booking (after a short delay, so the form's modal has closed; it doesn't wait for Apps Script) for `WhatsAppConfirmationDialog` in the root layout (a SwiftUI `Alert` on iOS, `showAlert` elsewhere).

**Styling:** plain `StyleSheet` with tokens from `src/constants/theme.ts` (`colors`, `spacing`, `radius`). The app is dark-only (`userInterfaceStyle: "dark"`) with a salmon accent, to match AppSheet. Each service's calendar colour is in `src/constants/services.ts`; use `serviceColor()`, which tolerates unknown values from old rows. On iOS the screens are SwiftUI (`@expo/ui`) in Liquid Glass style: use `glassButton()` / `glassProminentButton()` from `src/components/swiftui/glass.ts` instead of `buttonStyle('bordered' | 'borderedProminent')` (they fall back to bordered below iOS 26), and wrap modals in `SwiftModal`, which puts ✕ (left) and ✓ save or 修改 (right) in the native stack header with `Stack.Toolbar` (a SwiftUI `NavigationStack` bar doesn't show inside these native-stack modals). Details modals edit in place: 修改 swaps the content to the edit form, ✕ then leaves edit mode rather than closing, and delete is a red full-width row shown only while editing, at the bottom of the form: `DeleteConfirmButton` (`src/components/swiftui/`), which confirms with a native SwiftUI `ConfirmationDialog` rather than `showAlert`. Icons go through `src/components/Icon.tsx` (`expo-symbols`: SF Symbols on iOS, Material Symbols on Android and web).
